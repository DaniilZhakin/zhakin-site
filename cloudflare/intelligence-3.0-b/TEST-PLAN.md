# Intelligence 3.0-B — план фактической проверки

Статус: PREPARED / HOLD

Цель: перед включением сбора данных проверить, что сервис принимает только разрешённые обезличенные события и правильно отказывает во всех остальных случаях.

## Положительные проверки

1. `POST /api/events` с разрешённым `page_view` → ожидается `202`.
2. Разрешённые поля (`event_type`, `path`, `timestamp`, `referrer_class`, `content_id`, `schema_version`) → событие записывается в D1.
3. Серверное поле `received_at` создаётся сервером, а не берётся от клиента.
4. `OPTIONS` с разрешённым origin → `204` и корректные CORS-заголовки.

## Отрицательные проверки

1. Неизвестное поле → `400 unknown_field`.
2. Неизвестный тип события → `400 invalid_event_type`.
3. Неверный путь → `400 invalid_path`.
4. Неверная версия схемы → `400 invalid_schema_version`.
5. Явные признаки персональных данных/секретов в payload → `400 forbidden_data`.
6. Запрос больше 4096 байт → `413 payload_too_large`.
7. Неверный JSON → `400 invalid_json`.
8. Неразрешённый origin → `403 origin_not_allowed`.
9. `GET /api/events` или другой путь → `404 not_found`.
10. При отсутствии реальной базы D1 → `503 runtime_not_configured`.

## Что ещё обязательно перед PASS

- подключить реальный Cloudflare Worker;
- подключить D1;
- включить и проверить реальное ограничение частоты запросов;
- выполнить положительные и отрицательные проверки непосредственно в production;
- убедиться, что в GitHub и клиентском JavaScript нет секретов;
- проверить, что в базе нет IP, fingerprint, email, телефона, токенов и других запрещённых данных;
- проверить журнал ошибок без PII;
- только после этого перевести статус 3.0-B в PASS.

До этих проверок production-сбор данных не включается.
