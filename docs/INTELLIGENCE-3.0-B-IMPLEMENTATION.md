# Intelligence 3.0-B — подготовка серверного сбора событий

Статус: PREPARED / HOLD
Дата: 2026-09-08

## 1. Что делаем простыми словами

На сайте нужен отдельный безопасный сервис, который получает обезличенные сигналы о работе сайта. Сам сайт остаётся на GitHub Pages. Сервис сбора данных работает отдельно и не должен зависеть от доступности GitHub Pages.

Цель: понимать, какие разделы посещают, как люди переходят между страницами и какие действия вызывают интерес — без сбора персональных данных.

## 2. Единая реализация

Основной и единственный актуальный Cloudflare-контур находится в:

`intelligence/collector-cloudflare/`

Старый экспериментальный каркас `cloudflare/intelligence-3.0-b/` не является production-реализацией и не должен подключаться к сайту.

## 3. Endpoint и контракт

Каноническая точка приёма:

`POST /api/events`

Разрешённые события:

- `page_view`
- `navigation`
- `menu_interaction`
- `outbound_click`
- `contact_interest`
- `contact_action`

Разрешены только поля:

- `event_type`
- `path`
- `timestamp`
- `referrer_class`
- `content_id`
- `schema_version`

Неизвестные поля отклоняются. Сервер сам фиксирует время получения.

## 4. Защита

До production-запуска должны быть фактически проверены:

- HTTPS;
- строгий CORS для разрешённых origin;
- проверка схемы;
- ограничение размера запроса;
- ограничение частоты запросов;
- серверное время получения;
- отсутствие секретов во frontend;
- обезличенное хранение;
- правила хранения и удаления;
- журналирование ошибок без персональных данных.

Не собираем IP-адреса, отпечатки устройств, рекламные и сквозные идентификаторы, имя, телефон, e-mail, содержимое форм, пароли, токены и API-ключи.

## 5. Проверки перед запуском

Положительный сценарий:
1. разрешённое событие принимается;
2. сервер добавляет своё время;
3. данные сохраняются только в разрешённой обезличенной форме;
4. возвращается успешный статус.

Негативные сценарии:
1. неизвестный тип события — отказ;
2. лишнее поле — отказ;
3. слишком большой запрос — отказ;
4. неправильный формат — отказ;
5. запрещённый origin — отказ;
6. превышение лимита — отказ;
7. попытка передать запрещённые данные — отказ без сохранения.

## 6. Что считается PASS

3.0-B нельзя объявлять PASS по наличию кода или документации.

Для PASS необходимо фактически подтвердить:

- Worker развёрнут в production;
- endpoint отвечает в production;
- разрешённые события принимаются;
- запрещённые данные не сохраняются;
- CORS и rate limiting реально работают;
- D1 доступна с необходимыми правами;
- положительные и отрицательные тесты пройдены;
- production-сайт не содержит секретов;
- мониторинг ошибок работает.
