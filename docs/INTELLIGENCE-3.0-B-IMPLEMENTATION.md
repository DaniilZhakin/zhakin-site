# Intelligence 3.0-B — подготовка серверного сбора событий

Статус: PREPARED / HOLD
Дата: 2026-09-08

## 1. Что делаем простыми словами

На сайте нужен отдельный безопасный сервис, который будет получать обезличенные сигналы о работе сайта. Сам сайт останется на GitHub Pages. Сервис сбора данных не размещается в публичном репозитории как рабочий production-сервис.

Цель: понимать, какие разделы сайта посещают, как люди переходят между страницами и какие действия вызывают интерес — без сбора персональных данных.

## 2. Где будет работать сервис

Целевой вариант: Cloudflare Worker.

Хранение:
- Cloudflare D1 — основное хранилище событий и агрегированных данных;
- Cloudflare KV — техническое быстрое хранилище для служебных состояний, если оно понадобится.

Production-сбор не включается этим документом. Для запуска нужен фактический доступ к Cloudflare runtime/account.

## 3. Адрес сервиса

POST /api/events

Браузер сайта отправляет туда только разрешённые события. Сервер сам ставит время получения события.

## 4. Разрешённые события

- page_view — просмотр страницы;
- navigation — переход внутри сайта;
- menu_interaction — взаимодействие с меню;
- outbound_click — переход на внешний ресурс;
- contact_interest — интерес к контакту;
- contact_action — действие с контактом.

## 5. Формат события

Разрешены только поля:

- event_type — тип события;
- path — путь страницы;
- timestamp — время, переданное браузером как дополнительный сигнал;
- referrer_class — обезличенная категория источника перехода;
- content_id — идентификатор материала, если применимо;
- schema_version — версия формата.

Неизвестные поля отклоняются.

## 6. Что категорически не собираем

- IP-адреса в хранилище;
- отпечатки устройств;
- рекламные идентификаторы;
- сквозные идентификаторы между сайтами;
- имя, телефон, e-mail;
- содержимое форм;
- пароли, токены и API-ключи;
- любые секреты из публичного JavaScript.

## 7. Защита

Перед production-запуском должны быть реализованы и проверены:

- HTTPS;
- CORS только для публичного сайта жакин.рф и его canonical origin;
- строгая проверка формата события;
- ограничение размера запроса;
- ограничение частоты запросов;
- серверное время получения;
- отсутствие секретов во frontend;
- ограниченный доступ к аналитике;
- правила хранения и удаления данных;
- журналирование ошибок без персональных данных.

## 8. Проверки перед запуском

Положительный сценарий:
1. разрешённое событие принимается;
2. сервер добавляет своё время;
3. событие сохраняется;
4. в ответ возвращается успешный статус.

Негативные сценарии:
1. неизвестный тип события — отказ;
2. лишнее поле — отказ;
3. слишком большой запрос — отказ;
4. неправильный формат данных — отказ;
5. запрос с запрещённого источника — отказ;
6. превышение лимита запросов — отказ;
7. попытка передать персональные данные — отказ или удаление до сохранения, в зависимости от реализации.

## 9. Что считается готовностью 3.0-B

3.0-B нельзя объявлять PASS только по наличию этого документа.

Для PASS необходимо фактически подтвердить:

- сервис развёрнут;
- endpoint /api/events отвечает в production;
- разрешённые события принимаются;
- запрещённые данные не сохраняются;
- CORS работает корректно;
- ограничение запросов работает;
- D1/KV доступны только в рамках заданных прав;
- тесты положительных и отрицательных сценариев пройдены;
- production-сайт не содержит секретов;
- фактический мониторинг ошибок работает.

## 10. Текущий блокирующий фактор

Cloudflare runtime/account пока не подключён к рабочему контуру этого проекта. Поэтому production-сбор данных намеренно не запускается.

Следующий технический шаг после появления runtime: создать Worker, подключить D1, выполнить тесты, проверить production endpoint и только после этого рассматривать 3.0-B как PASS.
