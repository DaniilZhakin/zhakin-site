# ZHAKIN Wallet — архитектура и план поэтапного запуска

**Статус:** DESIGN / NOT PRODUCTION  
**Дата:** 2026-10-11  
**Контур:** официальный сайт Жакин.рф / ZHAKIN Digital

## 1. Назначение

Подготовить безопасную основу для персональных кабинетов участников, внутреннего учёта подтверждённой волонтёрской активности и начисления поощрительных баллов. Разработка ведётся поэтапно и не должна нарушать работу действующего сайта.

Рабочая модель названий:
- **ZHAKIN Digital** — цифровая экосистема;
- **ZHAKIN ID** — учётная запись участника;
- **ZHAKIN Wallet** — персональный интерфейс кошелька и истории операций;
- **ZHAKIN Points** — внутренние учётные баллы;
- **Activity Registry** — реестр заявок, заданий и подтверждённых действий;
- **Admin Control** — проверка действий координаторами и аудит.

Названия являются рабочими и не означают регистрацию товарных знаков.

## 2. Границы первой версии

Первая версия — внутренний учёт активности и баллов, а не финансовый продукт.

В первой версии ZHAKIN Points:
- не являются криптовалютой, электронными деньгами, ценной бумагой или банковским счётом;
- не имеют заявленной денежной стоимости;
- не обещают обмен на деньги, перевод между пользователями или вывод;
- не создаются и не выпускаются в блокчейне;
- начисляются только по заранее определённым правилам после проверки уполномоченным координатором.

Любые будущие вознаграждения от партнёров, конвертация, платёжные функции или токенизация требуют отдельной правовой, налоговой, финансовой и технической оценки до включения.

## 3. Архитектурный принцип

Текущий сайт работает на GitHub Pages и является статическим. Он может показывать публичное описание программы, но не должен самостоятельно хранить учётные данные, секреты, права доступа или авторитетный баланс.

Для работающего кошелька необходим отдельный серверный контур:
1. веб-интерфейс на Жакин.рф;
2. серверный API с аутентификацией и проверкой прав;
3. база данных с ограниченным доступом;
4. неизменяемый журнал операций (append-only ledger);
5. журнал административных действий;
6. резервное копирование, мониторинг и процедуры восстановления.

Cloudflare Worker / D1 могут рассматриваться как один из вариантов реализации после отдельной проверки текущего аккаунта, доступов, квот, резервного копирования и эксплуатационных ограничений. Наличие ранее созданного Worker для другой задачи не считается готовой инфраструктурой кошелька. Старые и помеченные как superseded эксперименты не подключать автоматически.

## 4. Основные сущности данных

### Participant
- внутренний случайный ID;
- статус учётной записи;
- дата создания и обновления;
- минимально необходимый набор профильных данных;
- согласия и версии применимых документов — только если юридически и технически обоснованы.

### Activity / Task
- ID задания или активности;
- описание и правила начисления;
- связанный проект;
- статус: draft, submitted, under_review, approved, rejected, cancelled;
- подтверждающие материалы — с отдельным контролем доступа и сроков хранения;
- ID участника и координатора, временные метки.

### Ledger Entry
- уникальный ID операции;
- ID участника;
- тип операции: accrual, reversal, adjustment;
- количество целых баллов (целое число, без float);
- основание и ссылка на подтверждённую активность;
- статус и серверная временная метка;
- ID инициатора и подтверждающего лица;
- idempotency key для защиты от повторного начисления.

Баланс рассчитывается из журнала операций либо поддерживается транзакционно обновляемым представлением, которое можно сверить с журналом. Нельзя принимать баланс от браузера как достоверный источник.

### Audit Event
- кто выполнил действие;
- что именно было изменено;
- основание, время и результат;
- без записи паролей, секретов и лишних персональных данных.

## 5. Безопасность и контроль

Обязательные условия до пилота:
- серверная аутентификация и авторизация для каждого приватного endpoint;
- принцип минимальных привилегий и разделение ролей участника, координатора и администратора;
- запрет начисления/списания из клиентского JavaScript;
- транзакционные изменения и защита от повторных запросов;
- журналирование каждой операции и отдельные корректирующие записи вместо удаления/перезаписи истории;
- ограничение частоты запросов, проверка входных данных и защита от CSRF там, где применимо;
- безопасное хранение секретов только в серверных настройках;
- отсутствие персональных данных в URL, открытых репозиториях и технических логах;
- резервное копирование и проверяемое восстановление;
- правила хранения и удаления данных, политика конфиденциальности и условия программы до приёма реальных участников;
- проверка доступности интерфейса на мобильных устройствах.

Никаких реальных участников и начислений до прохождения проверок и утверждения правил программы.

## 6. Роли и поток подтверждения

1. Участник входит в защищённый кабинет и видит собственный баланс и историю.
2. Участник отправляет отчёт о выполненном задании.
3. Координатор проверяет заявку и подтверждающие сведения.
4. При одобрении сервер создаёт ровно одну операцию начисления.
5. Участник получает запись в истории.
6. Ошибки исправляются отдельной операцией reversal/adjustment с указанием причины и ответственного лица.

Участник не может одобрять собственную активность или менять журнал. Администраторские действия подлежат аудиту.

### Release 1 — закрытый технический прототип
- API и схема базы данных в отдельном серверном контуре;
- тестовые аккаунты и синтетические данные;

- без публичной регистрации и без реальных начислений.

### Release 2 — ограниченный пилот
- только после проверки безопасности и утверждения документов;
- приглашённые участники, координаторская модерация, мониторинг и процедура инцидентов;
- возможность приостановить начисления без потери истории.

### Release 3 — расширение экосистемы
- профили активности, достижения и агрегированная статистика;
- партнёрские механики — только после отдельной правовой и операционной оценки.

### Release 4 — отдельное исследование токенизации
- не является автоматическим продолжением баллов;
- отдельное решение о правовом статусе, эмиссии, хранении, AML/KYC при применимости, налогах, безопасности смарт-контрактов и рисках;
- не смешивать с COIN УСЕРДИЕ / BFU и активами благотворительного фонда.

## 8. Критерии готовности

Нельзя объявлять кошелёк запущенным только потому, что опубликована страница или интерфейс.

Для допуска к пилоту требуется доказать:
- приватные endpoint недоступны без авторизации;
- роли проверяются на сервере;
- невозможно начислить баллы через подмену клиентского запроса;
- повтор запроса не создаёт повторное начисление;
- история не удаляется и корректировки объяснимы;
- данные одного участника недоступны другому;
- резервная копия восстанавливается;
- журналы не раскрывают секреты и избыточные персональные данные;
- тесты положительных и отрицательных сценариев пройдены;
- документы и правила программы утверждены ответственными лицами.
