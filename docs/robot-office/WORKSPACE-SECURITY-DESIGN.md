# ZHAKIN Robot Office — модель доступа и безопасного подключения

**Статус:** проектная спецификация; backend/API не реализован.
**Область:** Treasury Guard, Legal Counsel AI, ZHAKIN COMMAND AI и люди-руководители.
**Запрет:** не подключать production, Cloudflare D1, реальные документы, банковские счета, персональные данные или Wallet API до отдельного security review и тестирования.

## 1. Принципы
1. Deny by default: отсутствие явного разрешения означает запрет.
2. Human approval: робот готовит анализ и проект действия; человек утверждает юридически или финансово значимые решения.
3. Least privilege: казначей не получает юридические полномочия; юрист не получает казначейские полномочия; координатор не наследует полномочия специалистов.
4. Каждый запрос ограничивается организацией и записями, разрешёнными сервером. Идентификатор из браузера не доказывает право доступа.
5. Каждая задача, версия документа, проверка и передача имеют автора, время, источник и историю.
6. Никаких автономных платежей, подписей, юридически значимых отправок, выдачи ролей или изменений инфраструктуры.

## 2. Роли и полномочия

| Роль | Просмотр | Черновики | Утверждение | Запрещено |
|---|---|---|---|---|
| Treasury Guard | Разрешённые финансовые сводки и подтверждения | Сверки, отчёты, платёжный календарь | Нет | Платежи, изменение балансов и банковских реквизитов, назначение ролей |
| Legal Counsel AI | Разрешённые договоры, нормы и материалы | Правовые справки, перечни рисков, проекты документов | Нет | Подписание, представительство, отправка юридически значимых документов |
| ZHAKIN COMMAND AI | Только переданные сводки и метаданные | Сводный отчёт, маршрутизация задач | Нет | Наследование полномочий, чтение исходных документов без отдельного разрешения |
| Человек-казначей | Финансовый контур в пределах назначения | Финансовые документы и отчёты | По отдельной политике | Самостоятельное изменение системных ролей |
| Человек-юрист | Юридический контур в пределах назначения | Заключения и проекты | По установленному порядку | Финансовые операции |
| Администратор доступа | Метаданные пользователей и назначений | Запросы изменения доступа | Назначение/отзыв ролей с MFA и аудитом | Проведение финансовых и юридических действий |

Назначения ролей хранятся на сервере в отдельном реестре: subject_id, organization_id, role, scope, granted_by, granted_at, expires_at, revoked_at. Клиентские claims не являются источником истины. Нужны переаттестация и немедленный отзыв доступа.

## 3. Рабочие сущности
- Task: id, workspace, owner_role, status, priority, created_by, created_at, due_at, organization_id.
- Document metadata: id, workspace, classification, storage_key, version, checksum, created_by, created_at, retention_until. Файлы — только в приватном хранилище с короткоживущими подписанными ссылками; публичные URL запрещены.
- Evidence: id, task_id, source_type, source_ref, observed_at, checksum, confidence, notes.
- Approval: id, object_type, object_id, requested_by, reviewer_id, decision, reason, decided_at. Для значимых решений — MFA/повторная аутентификация и разделение обязанностей.
- Audit event: append-only событие с субъектом, ролью, действием, объектом, результатом, временем и request ID. Секреты и полные персональные данные в журнал не записывать.

## 4. Минимальные серверные операции (будущий API)
- GET /api/office/me — серверная идентичность и эффективные роли.
- GET /api/office/tasks?workspace=treasury|legal — только разрешённые задачи.
- POST /api/office/tasks — создать задачу или черновик; сервер назначает владельца и организацию.
- GET /api/office/tasks/{id} — серверная проверка доступа к конкретной записи.
- POST /api/office/tasks/{id}/handoff — передать сводку координатору без расширения доступа к оригиналам.
- POST /api/office/documents/metadata — зарегистрировать метаданные; загрузка только через контролируемый приватный upload flow.
- POST /api/office/approvals — запросить человеческое решение; операция не исполняет платёж и не подписывает документ.
- GET /api/office/audit — read-only для уполномоченного аудитора/администратора.

Все операции требуют аутентифицированной сессии, CSRF/Origin защиты для cookie-сессий, лимитов, схемной валидации, серверной проверки роли и scope, request ID и аудита. Нельзя доверять role, organization_id, owner_id, approved=true или storage_key из браузера.

## 5. Разделение данных
- Treasury и Legal — отдельные пространства данных и отдельные grants.
- Координатор получает минимальную сводку, но не доступ к исходным документам по умолчанию.
- Wallet/ZP не является источником банковских остатков и не смешивается с банковскими счетами.
- COIN УСЕРДИЕ (BFU) и ZHAKIN Points (ZP) остаются раздельными системами.
- Классификация документов: public, internal, confidential, restricted. Для restricted нужен индивидуальный grant и журналирование.

## 6. Обязательные проверки до интеграции
1. Unit tests матрицы ролей: разрешённые и запрещённые действия.
2. Integration tests на отдельной disposable SQLite/D1 базе: межорганизационная изоляция, доступ к чужому task/document ID, отзыв роли, истечение назначения.
3. Проверки эскалации: казначей → legal; legal → treasury; координатор → исходные документы.
4. Replay, повторный submit, параллельное изменение статуса, атомарность audit и rollback.
5. CSRF/Origin, session revocation, MFA для утверждений и ограничения upload.
6. Хранение, удаление по сроку, резервное копирование и восстановление.
7. Privacy/legal review до использования реальных персональных, финансовых или договорных документов.
8. Browser QA на iPhone и desktop, accessibility и отсутствие утечки данных через HTML/JS/source maps.

## 7. Критерии допуска
Интеграция допускается только после утверждения модели ролей человеком, реализации серверного enforcement, успешного прохождения disposable DB tests и security review. До этого кабинеты остаются статическими макетами, без реальных данных, загрузки документов и рабочих кнопок.
