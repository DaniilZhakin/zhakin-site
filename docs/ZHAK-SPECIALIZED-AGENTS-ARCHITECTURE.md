# ЖАК: архитектура специализированных агентов

**Статус:** проектная спецификация. Этот документ описывает целевую архитектуру; сам по себе он не создаёт и не запускает автономных агентов.

## Цели и принципы

ЖАК должен координировать узкие рабочие роли, а не выдавать один общий ответ за работу множества независимых систем. На первом этапе роли реализуются как изолированные модули/задачи внутри существующего backend. Отдельные сервисы или фоновые агенты допустимы только после самостоятельной оценки стоимости, доступа и отказоустойчивости.

Обязательные принципы:

- **Единый координатор:** принимает запрос, определяет нужные роли, собирает результаты и разрешает конфликты.
- **Минимальные права:** каждый исполнитель получает только нужные данные и инструменты; доступ на запись закрыт по умолчанию.
- **Доказуемость:** выводы сопровождаются источниками, временем получения и статусом проверки; недоступные данные не заменяются выдуманными.
- **Fail closed:** если источник, авторизация или проверка недоступны, система сообщает об ограничении и не совершает действие.
- **Человек утверждает рискованные действия:** публикации, изменения production, управление секретами, финансовые операции и юридически значимые действия не выполняются автономно.
- **Разделение секретов:** ключи остаются в server-side secrets; не передаются в браузер, промпты, логи или отчёты.
- **Наблюдаемость без лишних персональных данных:** фиксируются технический статус, длительность, тип задачи и ошибка; содержимое пользовательских обращений и секреты не отправляются в аналитику без отдельного обоснования и согласованной политики.

## Роли

| Роль | Ответственность | Доступ по умолчанию | Выход |
|---|---|---|---|
| Координатор | Классифицирует задачу, выбирает роли, объединяет результаты | Только необходимые метаданные и результаты подзадач | Ответ, план, список ограничений |
| Аналитик сайта | Анализирует посещаемость, просмотры, страницы и динамику | Read-only запрос к серверному PostHog-контуру | Метрики с периодом и статусом доступности |
| SEO-аудитор | Проверяет sitemap, robots, canonical, JSON-LD, внутренние ссылки и технические сигналы | Read-only репозиторий/публичные страницы | Отчёт с доказательствами и приоритетами |
| Исследователь и редактор | Готовит справки и аналитические материалы на основе доступных источников | Чтение публичных источников и библиотеки знаний | Черновик с цитатами, датами и оговорками |
| Технический агент | Анализирует код, тесты, конфигурацию и ошибки | Read-only по умолчанию; изменения только в отдельной ветке после разрешения | Диагностика, патч и план тестирования |
| Агент безопасности | Проверяет секреты, авторизацию, CORS, обработку ошибок, доступ к данным и границы интеграций | Read-only; без чтения значений секретов | Риски, критичность, рекомендуемые исправления |
| Контролёр качества | Проверяет источники, тестовые результаты, противоречия и полноту | Чтение результатов остальных ролей | Вердикт: подтверждено / требует проверки / отклонено |

## Поток выполнения

1. Координатор формирует задачу и критерии готовности.
2. Назначаются только необходимые роли; независимые read-only проверки могут выполняться параллельно.
3. Каждый результат содержит: вывод, источник/артефакт, время проверки, статус и неопределённость.
4. Контролёр качества проверяет подтверждения и ищет противоречия.
5. Координатор выдаёт итог и явно перечисляет незавершённые проверки.
6. Изменения кода — отдельная ветка и pull request; merge и production deployment — отдельные решения с явным подтверждением.

## PostHog: границы интеграции

- Серверный Worker читает `POSTHOG_HOST`, `POSTHOG_PROJECT_ID` и `POSTHOG_API_KEY` из runtime secrets.
- Браузер не получает API key и не обращается к закрытому API PostHog напрямую.
- Аналитическая роль использует только возвращённый сервером payload и сообщает период данных.
- Сбой или отсутствие credentials должны возвращать статус недоступности, а не синтетические метрики.
- Smoke test должен проверять не только HTTP 200, но и `configured=true`, `available=true` и наличие непустого payload. Он не должен печатать сам payload или секреты в CI-логи.

## Интеграции и границы возможностей

Наличие записи в реестре интеграций или доступного коннектора у оператора проекта не означает, что ЖАК имеет runtime-доступ к этому сервису. Каждая интеграция должна иметь отдельный адаптер, документированный контракт, ограниченный набор прав, тайм-ауты, обработку ошибок и тесты. Не заявлять о подключении до подтверждения реального успешного вызова.

## Критерии готовности первой версии

- [ ] Контракт ролей и координатора покрыт модульными тестами.
- [ ] Каждая роль имеет схему входа/выхода и ограничение времени выполнения.
- [ ] Ошибка одной роли не ломает весь запрос; частичный ответ маркируется.
- [ ] PostHog smoke test подтверждает реальный непустой ответ.
- [ ] Проверены CORS, ограничения запросов, rate limiting и отсутствие секретов в логах.
- [ ] Проведён read-only security review и проверены CI-результаты.
- [ ] Только после отдельного одобрения выполняются merge, подключение публичного endpoint и deployment.

**Важно:** на момент создания этой спецификации архитектура описана, но автономные роли ещё не считаются реализованными или работающими в production.
