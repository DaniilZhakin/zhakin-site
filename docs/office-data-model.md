# ZHAKIN TEAM OFFICE — модель данных и контроль доступа (проект)

Версия: 0.1  
Статус: проектная спецификация, не миграция и не подключённая база данных.  
Область: внутренние поручения, проекты, решения, согласования и аудит.

## 1. Принципы

1. **Источник истины — серверная БД.** Браузер и клиентские параметры не определяют пользователя, роль, область доступа или статус операции.
2. **Отказ закрывает доступ (fail closed).** Если проверка роли, области проекта или запись аудита недоступна, изменение не выполняется.
3. **Минимальные полномочия.** Роль ограничивается организацией/контуром и назначенными проектами; глобальные права выдаются отдельно и редко.
4. **Робот не является субъектом полномочий.** Агент может подготовить черновик/рекомендацию, но не утверждает решение, не меняет роли и не выполняет внешнее/финансовое действие.
5. **Неизменяемый след.** Существенные события записываются append-only; исправления оформляются новой записью, а не перезаписью истории.
6. **Разделение среды.** Разработка, тестовая БД и production имеют отдельные учётные данные и ключи. Никаких реальных операций до прохождения контрольных ворот.

## 2. Основные сущности

### users
- `id` — внутренний случайный идентификатор (не email и не публичный ID).
- `identity_provider`, `provider_subject` — уникальная связка внешнего провайдера и subject.
- `email_normalized` — nullable, уникальный только при подтверждённом адресе.
- `display_name`, `status`, `created_at`, `updated_at`.
- Пароли и OAuth-токены не хранить в этой таблице; секреты — только в управляемом хранилище/провайдере.

### organizations
- `id`, `name`, `status`, `created_at`.
- Организационный контекст для изоляции данных. Не полагаться только на скрытие элементов интерфейса.

### projects
- `id`, `organization_id`, `code`, `title`, `description`, `status`, `owner_user_id`, `created_at`, `updated_at`.
- Уникальный `code` в пределах организации; FK и индексы по `organization_id`, `status`.

### roles
- Справочник разрешённых ролей: `office_viewer`, `project_coordinator`, `document_editor`, `security_auditor`, `office_admin`.
- Роль сама по себе не даёт доступ ко всем проектам.

### user_role_scopes
- `id`, `user_id`, `organization_id`, nullable `project_id`, `role_id`, `granted_by_user_id`, `valid_from`, nullable `valid_until`, `revoked_at`, `created_at`.
- Изменение выдачи/отзыва прав требует отдельного разрешения и записи аудита.
- Проверка доступа всегда серверная: пользователь + организация + проект + действие + активный срок роли.

### tasks
- `id`, `organization_id`, `project_id`, `title`, `description`, `acceptance_criteria`.
- `created_by_user_id`, `assignee_user_id`, `priority`, `status`, `due_at`.
- `version` для optimistic concurrency; `created_at`, `updated_at`, nullable `completed_at`.
- Статусы: `draft` → `open` → `in_progress` → `blocked` / `in_review` → `done` / `cancelled`.
- Переходы статусов валидируются сервером. Закрытие требует результата и подтверждающего материала, если он предусмотрен критериями.

### decisions
- `id`, `organization_id`, nullable `project_id`, `title`, `decision_text`, `rationale`, `status`.
- `proposed_by_user_id`, nullable `approved_by_user_id`, `proposed_at`, nullable `approved_at`, `effective_at`.
- Статусы: `draft`, `submitted`, `approved`, `rejected`, `withdrawn`.
- Автор предложения не может сам утвердить решение, если политика требует разделения инициатора и утверждающего.

### approval_requests
- `id`, `organization_id`, `object_type`, `object_id`, `action`, `requested_by_user_id`, `approver_user_id`.
- `status`, `reason`, `requested_at`, `decided_at`, `decision_comment`, `version`.
- Согласование привязано к версии объекта. Изменение объекта после отправки аннулирует прежнее согласование и требует нового.

### audit_events
- `id`, `organization_id`, nullable `project_id`, `actor_user_id`, `actor_type`, `action`, `object_type`, `object_id`.
- `before_hash`, `after_hash`, `reason`, `request_id`, `created_at`, `outcome`.
- Только добавление; запрет UPDATE/DELETE для прикладных ролей. Не помещать в аудит пароли, токены, полные персональные документы или лишние персональные данные.
- Ошибка записи аудита блокирует критическое изменение в одной транзакции.

### evidence_files
- `id`, `organization_id`, `project_id`, `uploaded_by_user_id`, `storage_key`, `mime_type`, `size_bytes`, `sha256`, `classification`, `created_at`.
- Файл хранится в закрытом объектном хранилище; доступ выдаётся краткоживущей ссылкой после проверки прав. MIME, размер и содержимое проверяются на сервере.

## 3. Минимальная матрица полномочий

| Действие | Viewer | Coordinator (scope) | Document editor (scope) | Security auditor | Office admin |
|---|---:|---:|---:|---:|---:|
| Просмотр доступного проекта | Да | Да | Да | Да | Да |
| Создание/изменение поручения | Нет | Да | Нет | Нет | По отдельной политике |
| Назначение исполнителя в своём scope | Нет | Да | Нет | Нет | По отдельной политике |
| Подготовка документа/черновика | Нет | По разрешению | Да | Нет | Да |
| Утверждение решения | Нет | Нет по умолчанию | Нет | Нет | Только если явно делегировано |
| Просмотр журнала аудита | Нет | Ограниченно | Нет | Да | Да |
| Выдача/отзыв ролей | Нет | Нет | Нет | Нет | Только с отдельным подтверждением |

Никакая роль не подразумевает право на денежные переводы, управление кошельком, подключение биржи или публикацию внешнего сообщения.

## 4. API-контракт (проект)

- `GET /api/office/v1/projects` — список только в разрешённом scope.
- `GET /api/office/v1/tasks?project_id=...` — чтение после проверки scope.
- `POST /api/office/v1/tasks` — создание по allowlist полей; actor и organization берутся из серверной сессии.
- `PATCH /api/office/v1/tasks/:id` — обязательные проверка версии, разрешённый переход статуса и audit event.
- `POST /api/office/v1/decisions` — создание проекта решения.
- `POST /api/office/v1/decisions/:id/submit` — отправка на согласование.
- `POST /api/office/v1/approvals/:id/approve` или `reject` — только уполномоченный человек, с проверкой конфликта интересов и версии объекта.
- `GET /api/office/v1/audit` — только аудиторам и отдельно разрешённым администраторам.

Каждый запрос требует аутентифицированной сессии, CSRF-защиты для cookie-сессий, rate limit, schema validation, безопасного логирования и корреляционного `request_id`. CORS — allowlist, не wildcard.

## 5. Обязательные инварианты

- Нельзя доверять `user_id`, `role`, `organization_id`, `approved_by` или `status` из тела запроса без серверной проверки.
- Нельзя читать/изменять объект по ID без проверки принадлежности организации и проектного scope.
- Нельзя повышать собственную роль или назначать себе утверждающего.
- Нельзя повторно исполнять операцию при повторе запроса: idempotency key для критичных POST.
- Нельзя завершить задачу без проверки критериев завершения.
- Нельзя утвердить изменившийся после подачи на согласование объект.
- Нельзя выполнять критическое изменение без атомарной записи audit event.
- Ошибка авторизации возвращает безопасный отказ без раскрытия существования закрытого объекта.

## 6. Тест-план до подключения production

1. Матрица allow/deny для каждой роли, организации, проекта и действия.
2. IDOR: подмена ID чужого проекта/задачи/решения.
3. Попытки повысить роль через body, query, headers и массовое присваивание.
4. Истёкшие/отозванные права, смена роли во время активной сессии.
5. Гонки версий и повторные запросы/idempotency.
6. Попытка самоутверждения и согласование устаревшей версии.
7. Сбой аудита: транзакция откатывается, состояние не меняется.
8. Загрузка опасных/слишком больших файлов, проверка MIME и закрытых ссылок.
9. Проверка CSRF, CORS, rate limit, XSS и безопасных сообщений об ошибках.
10. Восстановление из резервной копии и проверка миграций на отдельной тестовой D1.

## 7. Ворота запуска

**G0 — проектирование:** согласованы роли, scope, модель данных, retention и threat model.  
**G1 — тестовая среда:** миграции применены на отдельной D1; тестовые пользователи и фиктивные данные.  
**G2 — безопасность:** интеграционные тесты, IDOR/privilege-escalation, аудит и восстановление прошли.  
**G3 — ограниченный пилот:** только чтение/несекретные поручения с ручным контролем и наблюдением.  
**G4 — production:** отдельное явное решение владельца, мониторинг, резервное копирование, incident runbook и процедура отзыва доступа.

До G4 офис остаётся демонстрационным интерфейсом. Wallet, биржи, бонусные переводы и внешние отправки не входят в этот scope и требуют отдельного security review.
